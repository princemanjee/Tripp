# Specification Engineering Template

A modular, versioned XML prompt template. Input: a drafted **user Specification Input** (a specification draft, user story set, or list of features and specs). Output: a complete **Specification Engineering Prompt** that directs a target AI coding agent to produce a five-artifact, git-managed Specification Stack (`CONSTITUTION.md`, `SPEC.md`, `PLAN.md`, `TASKS.md`, `EVALS.md`) and develop the user's requirements into a fully tested and functioning deliverable.

Generated by `PRPs/specification-engineering-template.md`, derived from `TemplateSpecs/ContextEngineringTemplatev4.xml`, incorporating the author directive of 2026-08-13 (eight-section specification anatomy, EARS-only functional logic, verification pipeline, Specification Stack).

## How to run

1. Load `SpecificationEngineeringTemplate-v1.xml` plus the modules its complexity route requires (see the `dependency_map` in the root document).
2. Supply the user Specification Input. `examples/SampleUserSpecificationInput.md` shows the expected shape, including the imperfections the template is built to catch.
3. The template intakes, routes, refines, populates, formalizes, and emits, per the Instruction module's `construction_cycle`.
4. Emitted artifacts land in `./output/`, named per the Output Contract emission rules: `SpecEngPrompt-[Subject]-v1.xml` and `Critique_[Subject]_[YYYY-MM-DD].md`.
5. The Specification Stack itself is produced later, by the target AI running the emitted prompt in the target repository.

`examples/WorkedExample-EmittedPrompt.xml` is the acceptance reference for the emission: what a correct emission from the sample input looks like under template v1.3, with all five PSpec elements (SP, EX, Q, OF, HP), EARS-only requirements, and the three planted defects surfaced in `Open_Questions` instead of silently resolved. `examples/WorkedExample-CritiqueTrail.md` is the acceptance reference for the critique trail that accompanies it: the five Process Artifact sections, the route decision as a five-row trigger table with the deciding input line per row, and the stage record naming which form of REFINE and FORMALIZE ran.

The `SampleInput-*.md` files are variation tests in the sense of the v4.0 base template's prompt testing framework: run the template against each and verify consistent quality across different domains and defect types. `SampleInput-MarkdownLinkChecker.md` is the one input built to fire none of the routing triggers, so it is the test of the Standard route and of the Standard-route forms of the REFINE and FORMALIZE stages; every other input routes Complex. Each preamble declares its planted defects so a tester can check the emission caught every one. Together the example inputs cover all seven intake validation rules: missing input, contradiction, token budget aside, context poisoning (ChatbotComplianceMonitor's unverified "11 states" claim), distraction, confusion, and context clash (OSHAReportingAutopilot's undecided pricing models). Every emission must hold each draft requirement built on a planted defect in `status="draft"` with a linked Open Question, exactly as `WorkedExample-EmittedPrompt.xml` demonstrates.

`GodelTerminal-CrawlInput.md` is not a variation test. It is the real-world demonstration input, derived from a permitted crawl of a live product, and it is the one used for the end-to-end chain proof of 2026-08-14: Specification Input to template to emitted prompt to executed prompt to a Specification Stack built in a separate repository. It plants no defects; what it exercises is scale and the quarantine of unquantified marketing claims.

## How to swap a module

Each root section resolves through a `<file_reference path="..." fallback="...">` element. To replace a module, author a new payload file following the same `{Name}_Payload` shape and point the `path` attribute at it. Nothing else in the root document changes. Keep the concepts marked `authoritative="true"` (`domain_signals`, `self_refine`, `ears_syntax`) defined in exactly one loaded module.

## How a fallback is selected

The `fallback` attribute names the lighter variant to load when the primary module is unavailable or when the Simple route makes the full module unnecessary. Intake, Requirements, and Verification have no fallback: intake is always required, and a lightweight EARS or verification module would defeat their purpose, so on routes that do not need them they are omitted entirely rather than thinned.

## Complexity routing

The route is decided by a procedure, not by judgement. Evaluate every trigger against the Intake classification, record each as fired or not fired with the input line that decides it, and carry the whole evaluation into the Process Summary of the critique artifact so the decision can be disputed by pointing at evidence.

| Route | Loads | Decision rule |
|---|---|---|
| Simple | Intake, Context, Output Contract | No trigger fired and the `simple_condition` holds |
| Standard | Simple + Instruction, Requirements | No trigger fired and the `simple_condition` does not hold |
| Complex | Standard + Verification | Any trigger fired |

The five triggers, any one of which routes Complex:

| Trigger | Fires when |
|---|---|
| T1 Regulated or sensitive data | The input names a regulation, standard, regulator, audit obligation, or compliance regime, or the system handles personal, financial, health, or safety data |
| T2 Multi-domain | Two or more `domain_signals` apply to the intended final state |
| T3 Stated invariant | The input marks a rule as holding regardless of mode, state, or actor, with an explicit marker such as absolute, non-negotiable, or in every mode. Only the marker fires it; a plain feature statement does not |
| T4 Irreversible external effect | The system makes payments, files with an authority, transmits to a third party, deletes user data, or actuates physical equipment |
| T5 Formal verification requested | The input asks for proofs, invariants, formal properties, or machine-checkable requirements |

The `simple_condition` is that the intended final state is a document or content artifact rather than a system whose behaviour must be specified, so no EARS requirement will be written. Where it is genuinely unclear whether a trigger fires, it fires: the Verification module costs a few dozen lines of context, a missed contradiction costs a shipped defect.

The root document's `complexity_routing` is authoritative for all of this. The table above is a reader's summary of it, not a second definition.

## Conventions

- Explicit open and close tag pairs; no self-closing form.
- Tabs for indentation, two per nesting level.
- No em dashes in prose; banner comments are the sole exception.
- Files under 1000 lines.
- Documents well-formed before they are returned.

## Versioning

Filename version mirrors the major digit of the `version` attribute in every file; minor revisions live in the attribute alone (the root is at 1.3 and the Instruction module at 1.2, both in `-v1` files). Changes follow the self-versioning protocol of the v4.0 base template (Appendix A): each new version opens with a critique log of dimensional scores and numbered revisions, and each is specified in the PRP before it is applied. See `VERSION_HISTORY.md`.
